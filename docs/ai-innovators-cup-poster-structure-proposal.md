# AI Innovators Cup向けSIT ORBITポスター構成案

## 結論

ポスターの主役は、SCombZ、SITRUS、My Library、CASTの機能一覧ではなく、必要な情報源だけを安全に使い分けて学生が今日の行動を決める流れにする。

推奨タイトルは次のとおり。

> SIT ORBIT
>
> 分散した学内情報を、根拠付きの「次の一手」へ。

副題では、SCombZ、SITRUS〈端末内〉、My Library、CASTを必要な時だけ使い分けるPersonal Campus Agentであることを説明する。

本提案では、回答へ結び付けた取得元と事実を**根拠（Evidence）**と呼ぶ。

「認証済み」や「連携済み」は、提出ビルドで実認証と実画面読取を再確認できたサービスにだけ付ける。

## 公式要件から導いた編集方針

作品提出ガイドでは、A0縦1枚のポスターが必須で、Web上でも公開される。

予選は審査委員90点と一般投票10点で構成される。

審査委員の評価観点は、AI活用の適切さ、プロンプト設計、人による判断と修正、オリジナリティー、見やすさの五つである。

観点別の配点は公開されていないため、特定の観点へ独自の重みを設定せず、すべての観点について採点可能な証拠を置く。

公式ガイドが例示する想定利用者、部門テーマとの関連、効果の確認方法も、上段または最下段で短く特定する。

## 過去開催記事から得られる補助情報

芝浦工業大学が公開した前回開催の記事では、既存AIサービスの組み合わせ方と、人による工夫、検証、改善の過程が評価対象だと説明されている。

したがって、「GPTを使った」という説明より、どの情報をAIへ渡し、どの情報を端末内に残し、どこで人が止めるかを具体的に示す。

## A0縦の推奨レイアウト

```text
┌──────────────────────────────────┐
│ 1. タイトルと一文の価値                         │
│ SIT ORBIT                                      │
│ 分散した学内情報を、根拠付きの「次の一手」へ。 │
├──────────────────────────────────┤
│ 2. 課題と、AIに任せる理由                       │
│ AI：意図理解、根拠整理、候補生成                │
│ コード：データ境界、Tool許可、書込み停止        │
├──────────────────────────────────┤
│ 3. 必要な情報源だけを選ぶ大きな中央図           │
│ SCombZ ─┐          SITRUS → 学生本人で停止       │
│ My Library ─┼→ 根拠付きNext Vector               │
│ CAST許可済み集計 ─┘      ↓                        │
│                  承認／変更／却下                │
├─────────────────┬────────────────┤
│ 4. 実プロンプト制約           │ 5. AI出力と人の修正         │
│ 原文抜粋＋出力Schema          │ 実際のBefore／After 1件      │
├──────────────────────────────────┤
│ 6. 実機確認／ローカル評価／未検証、3分デモQR     │
└──────────────────────────────────┘
```

上段12%で作品名、対象者、応募部門、価値を伝える。

次の14%で課題と、AIに任せる処理、コードで固定する安全境界を対比する。

中央42%は、一人の学生の質問から必要な情報源だけを選び、今日の一手を決める流れへ割り当てる。

次の24%は実プロンプトと人の修正例へ割り当てる。

最下段8%に実機確認、ローカル評価、未検証、QRコード、チーム情報、出典を置く。

この割合は公式配点ではなく、読解順を作るための紙面配分である。

## 中央に置く利用シーン

中央図は、四サービスを固定順で呼ぶ直列図にしない。

学生の質問から、その質問に必要な情報源だけを選ぶファネル型にする。

1. 学生が「表示中の授業を見て、次回までにやることを教えて」と尋ねる。
2. SCombZから課題、締切、教材の該当ページを取得する。
3. SITRUSの成績は端末内だけで学生本人が確認し、成績値を外部Agentへ渡さない。
4. 学生が自分の判断として「基礎から復習したい」と入力する。
5. My Libraryで貸出中、予約中、返却期限を確認し、公開OPACで候補図書を調べる。
6. CASTの求人、インターン、支援情報の詳細は端末内に残し、許可済みの匿名集計だけをAgentへ渡す。
7. Agentが許可済みEvidenceと学生自身の意図から今日の行動を一つ提案する。
8. 学生が提案を承認、変更、却下し、確定した結果だけを記録する。

SITRUSは同じ外部Provider会話へ混ぜない。

図ではSITRUSを橙色の「端末内」レーンへ分岐させ、線を学生本人で止める。

Agentへ戻るのは、学生が自分で入力した方針だけとする。

CASTも「端末内の詳細」と「Agentへ渡せる許可済み集計」を分ける。

My Libraryの予約やCASTの応募は、読取と操作可能性の確認までを示す。

実送信を検証していない操作は、「確認後も実行しない」と表示する。

## 五つの審査観点へ置く証拠

| 審査観点 | ポスターに置く内容 | SIT ORBITで使える証拠 |
| --- | --- | --- |
| AIの活用目的と方法 | AIに任せる処理と、コードで固定する処理を対比する | AIは質問意図の理解、根拠整理、行動候補生成を担当し、コードはデータ境界、Tool許可、Evidence検証、書込み停止を担当する図 |
| プロンプト設計 | 実際に使用する短い原文と出力Schemaを示す | Tool Catalogの概要を検索し、発見済みToolだけを使用、正確なEvidence ID必須、未知ID拒否、一つの行動を提案 |
| 人の判断と修正 | 実際のAI提案と最終決定を左右に並べる | 学生が変更した箇所を強調したBeforeとAfterの一件 |
| オリジナリティー | 四サービスを単に統合せず、データ境界を保って一つの判断へ収束させる | 今日の課題、端末内の自己確認、資料、将来の職種からNext Vectorへ戻る閉ループ |
| 見やすさと伝わりやすさ | 一枚の大きなファネル図、色分け、短い結論 | 主張、利用シーン、採点用証拠の順に読めるA0縦の情報配置 |

## プロンプト設計の見せ方

「プロンプトを工夫した」と書くだけでは、審査委員が具体性を評価できない。

説明文だけでなく、実装中のsystem promptから短い原文を抜粋し、Structured Outputの主要項目を隣へ置く。

```text
"Propose exactly one small action using only the supplied event and evidence."
"The external action must require confirmation."
"Use only these facts."
"Do not invent IDs or event details."

出力：title / reason / duration_minutes / evidence_ids / requires_confirmation
```

その下に、次の四つを短いカードとして載せる。

```text
入力を限定する
現在の質問、直近2件の文脈、利用可能なread-only Toolだけを使う。

Toolを限定する
認証状態、同意、データ分類を満たすToolだけをCatalogへ登録し、必要な定義はHosted Tool Searchで発見する。

回答を根拠へ拘束する
取得済みの正確なEvidence IDだけを回答へ添付し、未知IDを拒否する。

人へ戻す
一つの小さな行動だけを提案し、外部操作は必ず明示確認を要求する。
```

プロンプト全文を小さい文字で貼るより、各制約がどの失敗を防ぐかを一対一で示す。

## 人が判断、修正した点の見せ方

公式観点へ直接対応する主証拠は、アプリ利用時の実際のBeforeとAfterにする。

アプリ利用時は、同じEvidenceに対するAI提案と、学生が変更した最終行動を並べる。

この差分はデモで実際に操作し、画面と時刻を記録してから掲載する。

開発時の安全設計判断は補助証拠とし、余白がある場合だけ次から一つか二つを載せる。

| AIに任せない対象 | 人が決めた境界 | 理由 |
| --- | --- | --- |
| SITRUS成績の外部送信 | 成績は端末内表示に限定 | 能力や適性の推測と個人情報送信を防ぐため |
| 図書館予約とCAST応募 | previewまたは利用不可で停止 | submitとread-backを実環境で検証していないため |
| 学内Toolの自由選択 | 認証・同意済みのToolだけをCatalogへ登録 | 不要な個人データ取得と誤Tool呼出しを減らすため |
| 根拠のない回答補完 | `partial`、`unavailable`として表示 | 取得不能と該当なしを混同しないため |

ただし、実際のAI出力との差分として示す箇所には、保存済みの出力、コミット差分、評価ログなど、追跡できる証拠を用意する。

設計方針だけを架空のBeforeとして置かない。

## 掲載候補となる現時点の実測値

現行の評価データは、Azure Responsesの実モデルがToolを発見できるかを測る合成・公開ラベルである。
旧来のローカル語句routerやshortlistの測定値は、現行方式の実績として引き継がない。

| 指標 | 結果 |
| --- | ---: |
| 意味ラベル付き評価ケース | 48件 |
| Tool選択recall | Azure実モデルで重要ケース各3試行後に測定 |
| 不要Tool実行率 | Azure実モデルで5%以下を検証 |
| capability・一般会話・prompt injectionの学内データTool | Azure実モデルで0件を検証 |

B1大宮fixtureでは、ActionProposalのschema、Evidence添付、外部操作の確認必須を各1ケースで確認した。

これはAgent Harnessのローカル確認であり、SCombZ、SITRUS、My Library、CASTの実認証成功率ではない。

ポスターでは「合成・公開データ48ケース」と「Azure実モデル評価は検証中」と明記する。

平均候補数、Provider token、内部fixture名、未実施の成功率はポスターへ載せない。

## 連携状況の表示

四サービスへ同じ緑色の「連携済み」を付けない。

提出直前に実Chromeで再確認し、制作資料として次の表を実測値で埋める。

| サービス | 実装した読取 | データ境界 | 実認証結果 |
| --- | --- | --- | --- |
| SCombZ | 課題、授業、お知らせ、教材検索 | 関連本文だけを上限付きで送信 | `PASS / BLOCKED / 未再確認` |
| SITRUS | 表示中の成績表または通知書 | 端末内だけで表示 | `PASS / BLOCKED / 未再確認` |
| My Library | 貸出、予約、履歴、依頼状況 | 明示質問時の最小項目だけ | `PASS / BLOCKED / 未再確認` |
| CAST | 概要、検索、就活サポーター集計 | 匿名集計と型付き仮名projectionだけ | `PASS / PARTIAL / BLOCKED / 未再確認` |

ポスターでは大きな表を使わず、中央図の各サービスへ`実認証・実画面読取`、`端末内のみ`、`ローカル評価のみ`、`未検証`の状態バッジを一つ付ける。

外部書込みは別の灰色バッジにし、「未検証の予約、応募、提出は、確認後も実行しない」と表示する。

## 視覚設計

背景は白または濃紺の一色とし、情報の状態だけを色で分ける。

- 青：Agentへ渡せる最小Evidence
- 橙：SITRUSなど端末内だけの情報
- 緑：学生が判断した最終行動
- 灰：未確認または利用不可の外部操作

色だけに依存せず、各状態へ文字ラベルを付ける。

タイトルは80pt以上、節見出しは36pt前後、本文は22pt以上を目安にする。

中央の会話図と最終提案画面を最大の図版にし、画面キャプチャの羅列を避ける。

Web公開を前提に、氏名、学籍番号、成績、連絡先、Cookie、内部IDを載せない。

実画面を使う場合は撮影許可を確認し、合成データの場合は図の直下へ明記する。

## 一般投票への対応

一般投票の閲覧時間は公式資料に記載されていない。

そこで制作上の仮説として、専門外の閲覧者が上段と中央図だけでも価値を理解できるようにする。

上段だけで、誰のどの困りごとをどう変えるかが読めるようにする。

「21 Tool」「PydanticAI」「OpenAPI」などの実装語を主見出しにせず、詳細欄へ移す。

中央の会話図には、質問、四つの根拠、Next Vector、学生の判断だけを残す。

QRコードは3分以内のデモへ直接つなぎ、機能別の動画集ではなく同じ会話の続きとして見せる。

## 効果の確認方法

効果はまだ測定していない値を成果として書かず、提出時点で実行できる確認方法を示す。

- 学生が質問してからNext Vectorを決めるまでの時間
- 提案に一件以上の根拠が付いた割合
- 提案に対する承認、変更、却下の割合
- 未確認情報を`partial`または`unavailable`として示せた割合
- 未検証の外部書込みrequestが0件であること

ポスター上部には`対象：芝浦工業大学の学生`と`応募部門：[確定した部門名]`を置く。

オープンテーマ部門で提出する場合は、部門との関連を`AI × 学生の意思決定支援`と表現できる。

## 削る内容

- Tool名の全列挙
- UIへ到達できないCASTのモジュール群
- 未再確認の実認証成功を示すチェックマーク
- Azureやライブラリ名の過剰な構成図
- 「AIがすべて自動で行う」という表現
- 予約、応募、提出を完了できるという表現
- B3豊洲を検証済みとする表現

これらを削ることで、審査委員は五つの観点に直接対応する証拠を短時間で確認できる。

## 制作前に追加で必要な証拠

1. 四サービスを使う撮影用シナリオを、合成データまたは公開可能なデモデータで一度通す。
2. 各サービスを`PASS`、`PARTIAL`、`BLOCKED`、`UNAVAILABLE_EXPECTED`で記録する。
3. 学生がAI提案を変更した実際のBeforeとAfterを一件保存する。
4. Providerへ送った項目と端末内に残した項目をpayload previewで確認する。
5. 3分動画とポスターで同じ学生、同じ質問、同じEvidenceを使う。
6. A0原寸とA4縮小の両方で、本文と図中ラベルを読めるか確認する。
