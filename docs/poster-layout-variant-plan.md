# SIT ORBIT ポスター構成案

## 固定する構成

主領域は一本の縦線と一本の横線で四分割する。

- 左上：背景
- 右上：実装まとめ
- 左下：秘匿処理の仕組み
- 右下：今後

中央の循環矢印は、実行時のデータ転送経路ではなく、課題の観測、実装、制約の検証、改善を反復する関係を示す。

スクリーンショットには実画面、合成データ、未検証の別を明記する。
個人情報を含む実画面は使わず、合成データの画面を用いるか、必要箇所だけを切り出して不透明な矩形で伏せる。

## 案A：一画面注釈型

各象限に一枚の大きなスクリーンショットを置き、画面内の三、四点から周囲の説明へ注釈線を伸ばす。
四象限の形は揃えるが、説明項目は象限ごとに変える。

### 左上：背景

SCombZ、My Library、CAST、SITRUSの公開画面または合成画面を一枚のモザイク画像にする。

注釈候補：

- 課題と教材はSCombZにある。
- 図書の所在と利用状態は図書館側にある。
- キャリア情報と成績情報は別の認証画面にある。
- 学生が複数画面を行き来して照合している。

### 右上：実装まとめ

SIT ORBITの全画面Chatを大きく置く。

注釈候補：

- 質問から必要な学内Toolだけを選ぶ。
- 取得したEvidenceを回答の近くに表示する。
- 根拠付きのNext Vectorを一つ提案する。
- 学生が承認、変更、却下を選ぶ。

### 左下：秘匿処理の仕組み

Context Manifestまたは送信内容を確認できる実画面を置く。
該当画面が存在しない場合は、実画面の代わりに実装済みの状態表示を置き、隣にベクター図で処理を補う。

注釈候補：

- 表示中のページから必要項目だけを端末内で抽出する。
- Cookie、HTML、PDF本体、内部IDを送らない。
- SCombZとCASTの人物情報は会話単位で仮名化する。
- SITRUSの成績値は外部Agentへ送らない。

### 右下：今後

現在の`unavailable`、`reauth_required`、`write_form_not_verified`のいずれかが見える画面を使う。

注釈候補：

- 未検証の予約、応募、提出は実行しない。
- 正式な書き込み経路とread-backの検証が残る。
- B3 Toyosuは検証済み範囲として扱わない。
- 実利用者評価とA0原寸での可読性確認を行う。

### 中央

四本の矢印だけを置き、中央へ「課題を観測し、根拠をつないで改善する」と書く。
矢印には手順番号を付けない。

### 評価

一画面と説明の対応が明快であり、審査員が実装範囲を確認しやすい。
本命案とする。

## 案B：一続きの利用場面型

四象限を一つの利用場面の時系列として読む。
各象限には別々の画面を置くが、同じ質問と同じ合成学生を使う。

### 左上：背景

学生が四つのサービスを開いている状態を示す。
注釈線で、必要情報が別タブと別画面に分かれていることを示す。

### 右上：実装まとめ

同じ質問をSIT ORBITへ入力し、EvidenceとNext Vectorが返る画面を示す。
注釈線で、質問、Evidence、提案、判断ボタンを順に説明する。

### 左下：秘匿処理の仕組み

同じ会話について、端末表示と外部送信内容の差が分かる画面を示す。
注釈線で、削除された項目、仮名、端末内に残る成績を説明する。

### 右下：今後

同じ提案が外部操作の直前で停止している画面を示す。
注釈線で、preview、本人確認、read-back、実利用者評価を今後の検証として示す。

### 中央

循環矢印へ小さく「1 見つける」「2 つなぐ」「3 守る」「4 検証する」と付ける。

### 評価

短時間でも流れを理解しやすく、一般投票に向く。
一方で、各機能の網羅性は案Aより下がる。

## 案C：技術分解型

四象限の面積だけを揃え、スクリーンショットの枚数と説明位置は内容に合わせて変える。
統一するのは象限見出し、本文書体、注釈線の形式だけとする。

### 左上：背景

四サービスの小さな画面断片を並べる。
各断片から中央の「学生による照合」へ線を集め、情報の分散を示す。

### 右上：実装まとめ

Chat画面とEvidence詳細の二枚を上下に置く。
Chat画面からはTool選択とNext Vectorへ、Evidence詳細からは出典と状態表示へ線を伸ばす。

### 左下：秘匿処理の仕組み

実画面一枚と、端末、Projection、外部Agentの三段階を示す小さなデータフロー図を併置する。
画面上の項目とデータフロー上の残る項目、消える項目を注釈線で対応させる。

### 右下：今後

現在の利用不可表示と、三段階の検証計画を置く。
利用不可表示から「正式API」「previewと確認」「read-back」へ線を伸ばし、実装済みに見えないようすべて「未検証」と明記する。

### 中央

循環矢印の中へ「Evidence → Next Vector → 判断 → Event」と置く。
矢印は各象限の説明線と交差させない。

### 評価

技術的な説明量を最も増やせる。
ただし、縮小表示では注釈が読みにくくなるため、A4縮小とWebサムネイルでの確認が必要になる。

## 注釈線の共通規則

- 線の始点には小さな丸を置き、画面内の一要素だけを指す。
- 一つの線に一つの説明だけを対応させる。
- 線を交差させず、同じ辺から出る線は平行に揃える。
- 説明は見出しを含めて二行以内にする。
- 一枚の画面に付ける線は四本までとする。
- 矢印は処理の方向だけに使い、画面説明には矢印のない細線を使う。
- SITRUSの端末内境界だけをオレンジにし、他の注釈線は濃紺にする。
- スクリーンショットの下へ「実画面」「合成データ」「未検証」のいずれかを明記する。

## 制作順

1. 案Aの白黒ワイヤーフレームを作る。
2. 各象限で必要なスクリーンショットを合成データ環境から取得する。
3. 注釈文を実画面上の位置へ合わせて削る。
4. A0原寸、A4縮小、Webサムネイルで読みやすさを確認する。
5. 案Bまたは案Cを同じ素材で組み、案Aと比較する。
